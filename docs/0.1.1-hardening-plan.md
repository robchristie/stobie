## Outcome

Make the architecture described by the first vertical-slice report mechanically true without adding user-facing capability. The application must retain its current workspace and interactions while gaining same-frame preview consistency, narrow pane authority, an actual frame render plan, desired-set scheduling, exact camera history, bounded decoded thumbnails, honest metrics and semantic runtime evidence.

## Exploration question and exit condition

Question: what is the smallest composable set of boundaries that removes the current state mirrors and order-dependent behaviour while preserving one Rust application model on native and WebGPU?

Representative probes:

- an active linked-camera drag and wheel burst;
- rapid zoom across tile levels;
- demand disappearance before worker completion;
- browser worker construction and runtime failure;
- repeated thumbnail scrolling beyond one cache budget;
- saved layout/session restoration;
- warmed idle after all queues drain.

Evidence owners are focused GPU-free reducers and scheduler tests, renderer-plan tests, structured diagnostics, and the native/browser smoke harnesses. Exploration exits when one coherent candidate passes focused native and Wasm builds, all probes have deterministic assertions, and a release rapid-zoom profile can be compared with this exact baseline.

## Intended boundaries

- Feature pane modules receive immutable read models and feature-scoped sinks. They never receive mutable `Session`, complete diagnostics or renderer residency collections.
- Camera interaction interpretation yields one preview snapshot before demand, raster, vector, coordinate and overview output for that frame.
- `FrameOutput` owns intents, commands, desired demands, one `RenderPlan` and repaint state. Feature panes append typed render requests; the egui integration submits callbacks after pane presentation.
- The renderer is authoritative for GPU residency. The runtime learns admission and eviction through typed events; the application does not mirror scalar residency to decide what can draw.
- Runtime reconciliation compares each desired set with the previous set, uses bounded queues and exact request tokens, and rejects any completion that is no longer outstanding.
- Thumbnail pixels use a bounded CPU presentation cache populated from decoded worker output.
- Diagnostics name and measure only observable quantities. Unavailable timing or topology remains explicitly unavailable or planned.

## Delivery phases

1. Select the camera preview and command-history model with focused tests.
2. Land narrow pane modules and the real frame render plan in runnable form.
3. Land bounded tokenised scheduling, worker failure propagation and off-main-thread fixture production.
4. Land truthful metrics, decoded thumbnails and semantic smoke operations.
5. Compare release observations with the baseline, update the vertical-slice report, run `cargo xtask verify`, independently review the exact head and land through one pull request.

## Current decisions

- Preserve the existing restrained application composition; this is an architectural hardening pass, not a redesign.
- Prefer exact multi-pane camera commands over a persisted link-group schema change unless exploration proves an authoritative group camera materially simpler. This avoids unnecessary saved-session migration.
- Treat crate renaming as a terminal mechanical step after internal boundaries stabilise, and verify that no published/downstream contract exists before landing it.
